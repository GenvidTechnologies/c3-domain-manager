# Key dependencies — adoption history

Moved out of `CLAUDE.md` verbatim (apart from relative links) to keep the
always-loaded instruction files under Claude Code's size limit. `CLAUDE.md`'s
"Key dependencies" section keeps the operational rules — the two-place bump
rule, the stated floors, the `npm view` checks and their traps, and how to
prove a bump output-neutral. This page holds the record of *why* each floor is
what it is. Update it in the same commit as any floor change.

## What each package provides

`@genvidtech/c3source` (floor `^2.0.0`) provides the Construct 3 file walkers (`find_all_eventsheets_path`, `find_all_layouts_path`), the `EventSheet`/`Layout`/`FunctionParameter` types, the typed event-tree extractors `extractFunctions(sheet)` and `extractIncludes(sheet)` (since 1.1.0) — we consume both instead of hand-rolling the walk — and (since 1.4.0) `validateForEditor(sheet)` / `EditorValidationIssue`, which checks a parsed event sheet against the structural rules the C3 editor enforces on import; `editorValidation.ts` calls this per sheet to build the editor-strictness report. Since 1.5.0 it also exports `PROJECT_MANIFEST_FILE` (`"project.c3proj"`), used as the discovery marker in `resolveProjectRoot`. Since the 1.7.0 `@genvidtech`-scope migration, `openProject`/`C3Project` is **adopted**: `computeDomainData` and `validateEditorStrictness` open a project handle and use `findAllEventSheets()`/`findAllLayouts()`/`scriptsDir`/`hasEventSheets()` for file discovery (as of issue #37, `validateEditorStrictness` reaches `findAllEventSheets()` through `collectSectionFiles` rather than calling it directly, while still calling `hasEventSheets()`/`eventSheetsDir` itself) instead of the bare `find_all_*_path` walkers (which also makes a project missing `eventSheets/`/`layouts/` return empty rather than throw) — see `wiki/decisions/0008-adopt-openproject-option-a.md`. Since 1.8.0, addon attribution (`C3Project.collectAddonAttribution()` + `getUsedAddons`) is **adopted**: `computeAddonInventory` (`src/domain/addonInventory.ts`) cross-references the manifest's declared `usedAddons` against the addons each object type/family actually draws on, powering the `addon-inventory` CLI subcommand and MCP tool — see `wiki/decisions/0009-addon-inventory-project-wide-diagnostic.md`. Since issue #26, per-domain addon attribution (`attributeObjectType`/`attributeFamily`, the pure per-file counterparts to `collectAddonAttribution`) is also **adopted**: an opt-in `objectTypeDirs`/`familyDirs` classification dimension lets object types and families classify into domains the same way `eventSheetDirs`/`layoutDirs`/`scriptDirs` already do, and `computeDomainData` attributes each classified object type/family to its owning domain, surfaced as a per-domain "Addons used" section in the generated domain-index pages — see `wiki/decisions/0010-per-domain-addon-attribution.md`. Since issue #28, expression (member) reference coupling (`extractExpressionReferences`/`ExpressionReferenceToken`) is also **adopted**: `extractExpressionRefs` walks raw ACE parameter strings and `computeDomainData` resolves object/family member references into a third `expressionRefsFrom`/`expressionRefsBy` coupling edge (via an `objectNameIndex` built from the `objectTypeDirs`/`familyDirs` classification), aggregated under union semantics into health/boundary/context-map/domain-pages — see `wiki/decisions/0011-expression-reference-coupling.md`. Since issue #33, the generic walk `find_all_files_path(dir, predicate)` plus `isEditorLocalPath`/`EDITOR_LOCAL_EXCLUSIONS`/`C3_TS_DEFS_FOLDER` are **adopted**: `listUncategorized` (`src/domain/domainAnalysis.ts`) delegates its section walks to them instead of hand-rolled recursive `readdirSync` helpers, so `*.uistate.json`, `uistate/` contents and `tsconfig.json` stop being reported as uncategorized, and `findScriptEntries` applies the same rule at the directory level — see `wiki/decisions/0013-editor-local-exclusion-list-uncategorized.md`. **Scope narrowed in issue #47/#46/#51 (ADR 0017):** that delegation now covers **four** walks, not six — `eventSheets/`, `layouts/`, `objectTypes/`, `families/`. `listUncategorized` no longer walks `scripts/` at all; it delegates to `findScriptEntries`, which is a hand-rolled `readdirSync` walk by design (it must emit *directory* entries, which `find_all_files_path` cannot). **The `descend` parameter now has zero uses in `src/`** — deleting `collectRootScriptFiles` removed the only one, so it is no longer why the floor is load-bearing (see the floor note below). **Since issue #52 (ADR 0020), `find_all_files_path` itself also has zero uses in `src/`** — `listUncategorized`'s four remaining walks and `computeDomainData`'s section walks both moved onto the local `collectSectionFiles` seam (`classification.ts`, wrapping the already-adopted `C3Project.findAll*` methods, ADR 0008) instead of calling `find_all_files_path` directly. **Two things that walk did *not* provide had to stay local at every call site:** it throws `ENOENT` on a missing dir (an `fs.existsSync` guard), and it returns absolute native-separator paths (a `path.relative(...).replace(/\\/g, "/")` — the `g` flag matters on Windows). **Both obligations moved with the call sites in ADR 0020, and the first one *inverted* — do not re-add it.** `collectSectionFiles` owns the relativize for the four sections, and deliberately carries **no** `existsSync` guard: it goes through `C3Project.findAll*`, whose shared `findInSection` already returns `[]` for an absent section dir. Adding one back would be redundant, not defensive. `findScriptEntries` still keeps its own guard — but for its own hand-rolled `readdirSync` walk, not for this one. Since 2.0.0, `isGeneratedScriptOutput` and `SCRIPT_SOURCE_EXTENSIONS` are also **adopted** (issue #48, ADR 0021): `domainGenerator.ts`'s `findScriptEntries` and `domainAnalysis.ts`'s script walk import `isGeneratedScriptOutput` directly in place of the retired local `isCompiledSibling` predicate, and `classification.ts` re-exports `SCRIPT_SOURCE_EXTENSIONS` instead of defining it — see the floor note below and the Classification section of `CLAUDE.md` for what did and didn't transfer. Since issue #60 (ADR 0022), `isSectionItemName` is also **adopted**: `domainAnalysis.ts`'s `listInertOverrides` imports it directly at its one class-3 call site in place of the retired local section-source predicate. Unlike the script side's re-exported constant, its companion `C3_SECTION_ITEM_EXTENSION` is **not** re-exported from `classification.ts` — it is a string literal where the retired local constant was an array, so a bare re-export would change the published type. Note: c3source still ships further surface not yet adopted here — `comparisonSymbol`/`COMPARISON_OPERATORS`/`IMAGES_FOLDER` (new in 1.7.0; the comparison helpers were evaluated for issue #19 and **deferred** for lack of an integration site — this tool renders no condition/comparison params today), `walkFiles`, `validateEventForEditor`, and manifest/image drift detection; the **1.9.0 opt-in surface** evaluated and **deferred** in issue #33 for lack of an integration site — `detectReferenceIntegrity` and its four `detect*Issues` detectors, the manifest *write* surface (`serializeProjectManifest`/`writeProjectManifest`/`C3Project.writeManifest()`; this tool has never written a C3 source file), and `ManifestDrift.degraded` (drift detection is unreachable from `src/`); note `manifestTolerant()` is the one deferred item with a *real* site (`addonInventory.ts`'s `project.manifest()` read), so it is a behaviour proposal awaiting its own issue rather than a missing adoption; and the broader **`.c3addon`-package layer** (`readAddonPackage`/`parseAcesModel`/`parseAddonMetadata`/`findAllAddons`/`AcesModel`, new in 1.8.0 — no integration site, this tool reads no `.c3addon` packages) — candidates for a future audit, consistent with the "when bumping c3source, check whether new exports supersede local logic" guidance below. Also unadopted: `detectStrayFiles`/`StrayFile` (new in 2.0.0), evaluated and **declined** in issue #62 — see `wiki/decisions/0023-decline-stray-file-diagnostic.md`. `@genvidtech/mcp-utils` (floor `^0.10.0`) provides MCP plumbing (`ReadWriteLock`, `ExpectedChanges`, `exposeDocs`, `Logger`) and (since 0.3.0) the `loadProjectConfig(projectRoot, fileName, schema)` config loader plus its `isMcpError` guard — an async, never-throwing read+merge+zod-validate that returns either the typed config or a structured `CallToolResult` error — as well as the `paginatedContent` (paginated single-block response) and `READ_ONLY`/`REGENERATE`/`MUTATE` tool-annotation constants. Since 0.4.0 it also provides `mcpContent` (single-block result+footer helper) and `withMcpErrors` (wraps an async handler so thrown errors become `CallToolResult` errors; accepts an `onError` hook for side-effects on failure). Since 0.5.0 it provides `resolveRootFolder` (resolves a project root from an explicit path, env var, or `project.c3proj` marker discovery; returns `ResolvedRoot | CallToolResult`, never throws) along with the `ResolveRootFolderOpts`/`ResolvedRoot` types; adopted by `src/adapters/locations.ts`'s `resolveProjectRoot` to power `--project-dir`.

## When bumping mcp-utils

**When bumping `@genvidtech/mcp-utils`, audit `src/mcp/server.ts` for hand-rolled equivalents of its exported helpers** — the annotation constants, `mcpContent`, `paginatedContent`, and `withMcpErrors` all sat hand-rolled until the 0.4.0 bump adopted them (some had been available since 0.3.0). **The 0.7.0 floor is load-bearing for `OptimisticWatcher` + `ObservedState` (issue #68/#70, [ADR 0026](../decisions/0026-fs-watch-platform-confound-and-upstream-routing.md)), and that audit is what produced them.** `setupWatcher` had never been audited against `OptimisticWatcher`, which turned out to be its upstream equivalent — and the audit found the upstream one carried the *same* `txId` double-bump, because `ExpectedChanges.consume` is single-shot while Windows delivers two `fs.watch` events per write. So the fix went upstream first (`GenvidTechnologies/mcp-utils#12`) and shipped as 0.7.0's Layer 3, a content-fingerprint ledger with no timing term; this repo then adopted the whole watcher, which also retired the provably-dead `suppressWatcherDepth`. **It did *not* close the leaked `FSWatcher` handle (#70), despite `stop()` being the reason adoption looked like it would** — `shutdown()` calls `stop()`, but is wired only to `SIGINT`/`SIGTERM`, and a client disconnecting by closing stdin raises neither; the handle is `unref`'d in the watcher factory instead. **Two things that read as settled and are not:** `expected: ExpectedChanges` is a *required* option, so adoption does **not** retire that import; and `suppress()` is async-only, so `writeDomainConfig` stays synchronous by calling `expect()` instead — Layer 2 exists precisely for events arriving after the suppress window closes. Verify a release's actual API against the packed types (`npm pack @genvidtech/mcp-utils@<version>` → `package/dist/*.d.ts`), not just the release notes — **and read the packed `.js` when the question is about runtime *behaviour* rather than shape** (which argument a parameter applies to, what a default actually does, whether a guard is inherited). A `.d.ts` cannot express those, and issue #33 nearly shipped a worse-than-default mechanism on a `.d.ts`-only reading. **The 0.8.0 floor is load-bearing for `exposeDocs`'s new `{ docsDir, recursive }` options (issue #74)** — `docsDir` lets the exposed resource root move off the default `"docs"` folder, and `recursive` walks its subdirectories, which together are what let the documentation tier retire `docs/` and move onto the `wiki/` bundle's nested `reference/`/`process/`/`decisions/` layout. **The 0.9.0 floor is load-bearing for two adoptions that shipped in the same release (issue #77, ADR 0028).** First, the txId codec — `formatTxToken`/`parseTxToken`/`compareTxToken`/`isValidProjectId` — adopted for the composite `<projectId>:<n>` wire token that replaces a bare per-project integer; it was requested upstream (`GenvidTechnologies/mcp-utils#19`) rather than implemented locally so the codec is one implementation shared with `construct3-chef#95` instead of two that can silently drift, since a token-format divergence between two servers an agent drives in one turn fails silently at the comparison rather than loudly at the call. Second, `resolveRootFolders` — the plural root resolver, adopted for the `server` subcommand's multi-root discovery — which **reverses a decline**: the design had declined auto-discovery because `resolveRootFolder` returns an `mcpError` on ambiguity and `mcpError` flattens its candidate list into the error text, leaving the matches structurally unrecoverable; 0.9.0's plural instead returns `{ paths, source }` where two-or-more matches is a *success* carrying every candidate, so the decline's sole premise stopped holding. **The 0.10.0 floor is load-bearing for `parseTxToken`'s discriminated `TxTokenParseResult` and its `TxTokenParseFailure` reason union (issue #79, [ADR 0029](../decisions/0029-txid-rejection-diagnostics.md))**, adopted in `src/mcp/server.ts`'s `checkTxToken` so a malformed `txId` is diagnosed distinctly from a stale one instead of being told the state changed and to retry — a remedy that can never work when the caller's token generator is what is broken. **Note what makes that floor load-bearing *in `src/`* at all**: the two symbols `src/` already imported, `formatTxToken` and `compareTxToken`, did **not** change in 0.10.0 (`formatTxToken` byte-identical; `compareTxToken` one token, `parsed !== null` → `parsed.ok`, same truth table), so before this adoption the new floor would have been load-bearing only in `test/` — which is a weaker claim than it looks, and the reason the adopt-or-decline question was worth a record rather than a silent skip. `compareTxToken` remains the sole accept/reject authority and the parse result is used only to render, so the adoption provably cannot change which writes are accepted.

## When bumping c3source

**When bumping `@genvidtech/c3source`, check whether new exports supersede local C3-parsing logic** — c3source owns the Construct 3 platform facts, so its releases tend to ship primitives that retire hand-rolled equivalents here. `extractFunctions`/`extractIncludes` (1.1.0) retired the local `src/domain/extraction.ts` walk in 0.2.0; `validateForEditor` (1.4.0) was adopted as `editorValidation.ts`; and 1.4.0's event-var-reference primitives (`getEventVarReferenceName`/`EVENTVAR_REFERENCE_ACES`, plus `visitEvents`/`hasConditions`/`hasActions`) were adopted in issue #14 — `computeDomainData` uses them to derive the second coupling source (`referencesFrom`/`referencedBy`); and `openProject`/`C3Project` (its section-dir coverage completed in 1.6.0/1.7.0) was adopted in issue #19 — `computeDomainData`/`validateEditorStrictness` use it for file discovery (ADR 0008); and 1.8.0's `collectAddonAttribution`/`getUsedAddons` were adopted in issue #25 as the project-wide `addon-inventory` diagnostic (ADR 0009); issue #26 then adopted the per-file `attributeObjectType`/`attributeFamily` counterparts as a per-domain addon-attribution diagnostic atop a new `objectTypeDirs`/`familyDirs` classification dimension (ADR 0010); and 1.8.0's `extractExpressionReferences` was adopted in issue #28 as the third cross-domain coupling source (`expressionRefsFrom`/`expressionRefsBy`, ADR 0011); and 1.9.0's caller-controlled `descend` parameter on `find_all_files_path`, with `isEditorLocalPath`/`C3_TS_DEFS_FOLDER`, was adopted in issue #33 to retire the last two hand-rolled `readdirSync` walks in `domainAnalysis.ts` (ADR 0013) — **but `descend` was then un-adopted in issue #47/#46/#51 (ADR 0017), which deleted its only call site. Do not cite `descend` when auditing why the floor is load-bearing: it no longer rests solely on `C3_TS_DEFS_FOLDER` (still consumed by `isReportableScriptDir`) — the 2.0.0 bump (issue #48, ADR 0021) added `isGeneratedScriptOutput` and the upstream-sourced `SCRIPT_SOURCE_EXTENSIONS` as further load-bearing reasons, described below. The floor is not ceremonial — but its justification moved, and that is exactly the kind of fact that reads as droppable to someone who only greps for the old reason.** Issue #52 (ADR 0020) continued the pattern: `find_all_files_path` itself lost its last call site too, retired in favor of the local `collectSectionFiles` seam — cite neither it nor `descend` when auditing the floor. As with mcp-utils, treat the release notes as a hypothesis and verify the actual surface against the packed `.d.ts` — **the issue's own example code is a hypothesis too**: #33's proposed predicate was wrong, because `find_all_files_path`'s `predicate` gates *files* by bare basename while `descend` gates *directories*, and neither inherits the other's editor-local filtering (the packed `.js`, not the prose, is what settled it) — **and `isEditorLocalPath` itself takes a bare *segment*, not a path**: hand it a multi-segment path and only the `.uistate.json` suffix test can fire, since `uistate`/`ts-defs` match as whole directory names and `tsconfig.json` matches exactly, so every other exclusion silently under-matches. A caller testing a *path* must walk its segments — `listInertOverrides` does, and that argument contract is where issue #36's `ts-defs/` trap lives (ADR 0018) — **and confirm the integration site the issue assumes actually exists** (issue #12 framed `validateForEditor` as a guard "before write-out," but this tool never writes C3 sheets, so it became a read-side diagnostic instead). **`SCRIPT_SOURCE_EXTENSIONS`'s retire-trigger fired and has been acted on.** `src/domain/classification.ts` (the `.ts`/`.js` script-source list, issue #39 / ADR 0016) used to be marked temporarily local, because 1.9.0 exported no script-extension constant (`findAllScripts` hardcoded `.ts` and excluded `.d.ts`). `GenvidTechnologies/c3source#73` requested it and closed merged on 2026-08-10, settling the `.js`/`.ts` disambiguation as a C3 platform fact rather than consumer policy (C3's own folder-project reconcile path implements exactly that rule); c3source 2.0.0 then shipped both the constant and its companion predicate `isGeneratedScriptOutput`, and issue #48 (ADR 0021) adopted both — `classification.ts` now re-exports `SCRIPT_SOURCE_EXTENSIONS` instead of defining it, and the local `isCompiledSibling` predicate it used to also define is **retired**, replaced at its two call sites by upstream's `isGeneratedScriptOutput`. `isScriptSourceName` (the admission predicate) stays local and is **deliberately not** replaced by upstream's same-named function: upstream's excludes `.d.ts`, where this tool must admit it to keep ADR 0013's `ts-defs/` exemption indexable — pinned by a cross-library test in `test/domain/scriptSurfaces.test.ts`. **A second, separate upstream question: `GenvidTechnologies/c3source#76`** asked whether the four section collectors' extension policies were intentionally inconsistent (`findAllEventSheets`/`findAllFamilies` filtered to `.json`; `findAllLayouts`/`findAllObjectTypes` didn't — measured, ADR 0017). c3source 2.0.0 answered it by unifying all four finders to filter `.json` upstream, via the AUDITED `isSectionItemName`/`C3_SECTION_ITEM_EXTENSION`. **The local section-extension constant and predicate's own retire-trigger has since fired too, and issue #60 (ADR 0022) acted on it.** ADR 0020 had been misread here as holding the `.json` list as this repo's own policy — that framing was a `CLAUDE.md` gloss, never ADR 0020's own text, which adopted `.json` as "c3source's own documented convention, not inventing a new one." With upstream's predicate agreeing with the retired local one on every basename measured, the re-examination concluded in retirement — but **note the route, because it is the part that generalizes**: `#73` was a *deletion trigger* that fired on its own, while `#76` was only a *prompt*, and it took issue #60 examining the question to reach the same destination. Same outcome, different mechanism; do not collapse the two when the next upstream question closes. See the Classification section of `CLAUDE.md` for what did and didn't transfer, and `wiki/decisions/0022-section-extension-provenance.md` for the full accounting.
