# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@CONVENTIONS.md

## What this is

`c3-domain-manager` analyzes Construct 3 projects through a domain-driven-design lens. It reads a `domain-config.json` from the *target* project's root (the current working directory, **not** this repo) and writes output to `extracted/` there, then produces a markdown domain index, health/coupling metrics, boundary validation, glossary collision checks, a context map, and editor-strictness diagnostics. Three locations are overridable: `--project-dir <path>` selects the C3 source root (default: auto-detected via `project.c3proj` discovery in the current dir or an immediate child, else cwd; also honoured via `C3_PROJECT_DIR`); `--config <path>` selects the config file; and `--extracted <path>` selects the output directory (use `none` for an ephemeral temp dir, auto-cleaned on exit). Relative paths for `--config` and `--extracted` resolve against the project root; relative paths for `--project-dir` resolve against the current working directory. The same capabilities are exposed both as a CLI and as an MCP server (stdio); the MCP server receives the resolved locations via `startServer(loc)`.

Read `docs/domain-architecture.md` for the domain model concepts and the full `domain-config.json` schema.

## Commands

```bash
npm run build       # tsc → dist/, then inject a #!/usr/bin/env node shebang into dist/cli.js
npm test            # pretest materializes the fixture, then mocha + tsx over test/**/*.test.ts
npm run lint        # eslint, --max-warnings 0 (CI fails on any warning)
npm run typecheck   # tsc -p tsconfig.test.json --noEmit (type-checks src AND test)
npm run fixture:prep # rebuild test/fixtures/canonical/ from the construct3-sample submodule
npm run corpus:scan -- <dir>  # authored-script population across a local C3 corpus
```

Run a single test file: `npm run test:file -- test/domain/health.test.ts`

`npm run test:noexit` is `npm test` **without `--exit`**, for checking that nothing leaks a
handle. `--exit` makes mocha kill the process once the suite finishes, which is what stops a
stray handle from hanging the run — and equally what stops anyone noticing there is one. The
MCP harness spawns a subprocess per suite (ADR 0025), so that check has a live subject now;
it is how acceptance row T2 was verified in issue #67. **Its mocha flags duplicate `test`'s by
hand — change one and change the other**: there is no `.mocharc*` file in this repo, so every
mocha flag lives inline in the `package.json` script that uses it, with nothing holding the
three test scripts in common.

`corpus:scan` answers the recurring "how many X are there really, across real projects"
question that several ADRs rest on (0009, 0016, 0021) — `.ts`/`.js` sibling pairs, orphan
`.js`, per-project totals. It takes corpus roots as arguments or via `C3_CORPUS_ROOTS`,
never hardcoded, since the corpus is machine-local and this repo's docs convention forbids
committing such paths. It anchors discovery on `project.c3proj` — **a scan keyed off
directory names instead would walk a project's own `extracted/` tree, which contains
`eventSheets/`, `layouts/` and `scripts/` directories, and silently count generated output
as source.** It also flags likely duplicate checkouts of the same upstream project rather
than silently double-counting them into the totals. Re-run it instead of citing a figure
from an older record: the numbers were measured, and the corpus moves.

**Use `test:file`, not `npm test -- <path>`, and not a bare `npx mocha`.** Two
separate traps. First, mocha *merges* a positional path with the spec glob
configured in the script rather than overriding it, so `npm test -- test/domain/health.test.ts`
silently runs the **whole** suite. Second, `npm test`/`npm run test:file` fire a
`pretest`/`pretest:file` hook that materializes the canonical fixture; invoking
`npx mocha` directly skips it, and the fixture-backed tests then fail (loudly —
see below).

Note: both local development and CI use `npm` for these script names. CI runs the shared `public-github-actions` Node gate (`.github/workflows/ci.yml`).

**That gate is `runs-on: ubuntu-latest` with no OS matrix, while development here is on Windows — so a green local run and a green CI run verify different things.** Anything whose correctness is platform-shaped is structurally invisible to CI: path separators most of all, but also case-sensitive filename collisions and file-locking behaviour. The concrete instance: `path.relative` emits backslashes on Windows and never on POSIX, so `.replace(/\\/g, "/")` is a **no-op** under CI and every filesystem-driven test passes identically with or without the `g` flag — both copies of that idiom were CI-untested for the life of the codebase, and the gap was invisible precisely because the tests that *looked* like coverage do pass on a developer machine (issue #37, [ADR 0024](docs/decisions/0024-editor-validation-single-enumeration.md)). So a test for platform-shaped behaviour must **synthesise** its input rather than walk a real directory — `test/domain/sectionSurfaces.test.ts` does this by stubbing a collector result, and looks artificial for that reason. **That prescription covers platform-shaped *data*; it does not reach platform-shaped *runtime behaviour*, which has no input to stub.** Separators are data — synthesise them and the test stops depending on the platform. When the OS itself is what differs, there is nothing to synthesise short of stubbing away the thing under test. Two measured instances, both from issue #67: `fs.watch` delivers **1** event per `fs.writeFileSync` on Linux ext4 and **2** on Windows — the mechanism behind #68's `txId` double-bump; and `chmod 0o444` blocks a write at uid 1000 (`EACCES`) but **not** at uid 0, where root bypasses the permission check entirely. **The first of those is platform-determined, not node-version-determined** — issue #67 measured it only on node 24/Windows and node 20+22/Linux, so platform and node major were confounded and [ADR 0025](docs/decisions/0025-mcp-server-stdio-test-harness.md) explicitly declined to settle which mattered; a 24-run 3×2 matrix in issue #68 since found the split invariant across three node majors on each side, so the cause is `ReadDirectoryChangesW` vs inotify ([ADR 0026](docs/decisions/0026-fs-watch-platform-confound-and-upstream-routing.md)). Cite the node versions as incidental if you cite them at all. For this kind, a test either asserts only what holds on both platforms, or **gates at runtime on *observing* the behaviour** rather than on a platform or uid guess — `test/mcp/writeFailure.test.ts` is the exemplar, asserting the full trajectory when it observes the behaviour and logging an explicit note and passing when it does not, so CI (which sees neither) cannot go red for a reason unrelated to the code. **`test/mcp/mutation.test.ts`'s K3 was the second exemplar and deliberately is not any more** — once #68 was fixed the trajectory became identical on both platforms, so there was nothing left to gate on, and a gate that asserts only when the bug appears is indistinguishable from one that never fires because the watcher is dead. **That is the shape's expiry condition, and it is worth stating because nothing detects it:** an observation gate is correct while the divergence is real and becomes a liability the moment it is not, yet it keeps passing either way (issue #68, [ADR 0026](docs/decisions/0026-fs-watch-platform-confound-and-upstream-routing.md)). Probe for the property rather than inferring it from a proxy: `process.getuid?.()` is `undefined` on Windows, where the read-only attribute blocks the write regardless, so a uid check cannot even express that case. Note the gate lives in another repo, so adding a Windows leg is a cross-repo change, not a local one.

**Formatting is unenforced — `npm run lint` is the only style gate.** A `.prettierrc.json` exists but prettier is **not** a dependency (not in `devDependencies`), there is no `format` script, and `eslint-config-prettier` turns off eslint's formatting rules. So **do not run `npx prettier --write` across files** — it pulls a transient prettier from the npx cache and reflows unrelated pre-existing lines, polluting the diff (this bit two tasks in the issue #28 work). Match the surrounding style by hand and keep any reformatting scoped to the lines you actually change.

**Cutting a release:** see `docs/releasing.md`. In short — bump the version in `package.json` + `package-lock.json`, commit `chore: Release X.Y.Z`, push a lightweight `vX.Y.Z` tag; the tag push triggers `.github/workflows/publish.yml` (OIDC trusted publish to npm).

## Branching

Base branch is `main`. Feature branches are `<type>/<issue-number>-<kebab-slug>`, where `<type>` is the conventional-commit type the work will land under:

```
test/34-construct3-sample-fixture
fix/33-editor-local-exclusion-uncategorized
feat/30-hub-coupling-discount
docs/42-claude-md-contract-sections
```

**The `<type>/` prefix and the issue number are both load-bearing** — a few pre-#16 branches omit the number (`feat/project-dir-source-root`), but every recent one carries it. Inferring the shape from `git log` alone gets this wrong: branch names survive only in PR metadata after a squash merge, so `main`'s history shows none of them. This is exactly how issue #38's branch was first created as `38-consolidate-test-helpers`, missing the prefix.

PRs are **squash-merged**, so the branch's individual commits do not reach `main` — one PR becomes one commit. Rebase onto `main` rather than merging into the branch.

## Commit Format

Conventional-commit type, colon, then a **capitalized** description:

```
<type>: <Description>
<type>: <Description> (#<issue>)
```

Types in use: `feat`, `fix`, `test`, `docs`, `chore`. The issue reference is optional in the subject and appears on roughly half of merged work; when present it goes at the end. GitHub's squash merge appends the PR number, so `main` ends up carrying both — issue first, PR appended:

```
fix: Exclude C3-editor-local artifacts from list-uncategorized (#33) (#40)
```

Bodies are welcome and used freely on branch commits — they are the natural place to record *why* a mechanism was chosen, and what was verified. They do not survive the squash, so anything that must outlive the branch belongs in an ADR or in this file, not only in a commit message.

## Pull Request Format

Title matches the intended squash subject (same conventional-commit shape as above). Body structure, consistent across recent PRs:

```markdown
## Summary
- Bullets with **bolded lead phrases**. State what changed, and what a reviewer
  should be skeptical about — not just an inventory.

Closes #<issue>

## Where the issue was wrong
Optional. Used when implementation reconciled a premise the issue got wrong;
the issue body gets annotated too, with its original text preserved.

## Changes
### <Area>   ← Core / Tests / Docs / Fixture plumbing / Guards …

## Notes for reviewers
Optional. Cross-repo dependencies, pushed upstream tags, things that will look
surprising in the diff.
```

`Closes #<issue>` is what links the PR to its issue — without it a merged PR leaves its issue open indefinitely, and already-shipped work resurfaces as plannable backlog.

## Key dependencies

**Bumping either dependency is a two-place change: `package.json` *and* the stated floor in this file.** The floors below are documentation, so they drift silently — a bump that updates only `package.json` leaves this file asserting a version the code no longer requires (caught by code review in issue #33, after the fact). Update both in the same commit, and add the adoption to the "When bumping …" chain below so the *reason* the new floor is load-bearing is recorded, not just the number.

**Nothing here detects that a release has happened — run `npm view <pkg> dist-tags` before trusting any version claim in this file.** The chain below is full of *forward-looking triggers* ("re-check on the next bump", "the next release fires this trigger"), and every one of them fires on an event outside this repo that no test, lint rule, or CI gate observes. The failure is silent and the prose stays fluent: this file asserted c3source 1.9.0 was latest and `c3source#73` unreleased for some time after **2.0.0** had shipped — carrying `SCRIPT_SOURCE_EXTENSIONS` and `isGeneratedScriptOutput`, the two things those triggers were waiting for (issue #48, [ADR 0021](docs/decisions/0021-decline-drift-diagnostic.md)). It was caught only because a task happened to check npm. **Note the direction of the risk**: the rest of this section tells you how to *verify a release you have already decided to adopt* (`npm pack`, read the packed `.d.ts`, read the packed `.js` for behaviour) — it does not tell you a release exists. Those are different questions, and only the second one goes stale on its own. A dependency major can also land *mid-task* and invert a claim this file makes, so a check at the start of a long task is not a check at the end of it.

**Two traps when running that check.** First, **this package publishes as `@genvidtech/c3-domain-manager`** — bare `c3-domain-manager` is somebody else's name and 404s, so a check written against it never answers the question it looks like it answers. Second, **do not run `npm view` under `2>/dev/null`**: with stderr discarded a 404 and a real answer are indistinguishable, and if the command sits in a chain beside a working one, the working one's output reads as though it belonged to both. That is exactly how a wrong package name reached a pre-committed acceptance criterion in issue #60 — the 404 was invisible and a sibling call printed a plausible `latest: 0.7.0`.

**Proving a bump changed no output has no supported route, so here is the one that works.** The central safety question on any dependency bump is whether the analysis output moved, and a green suite is a weaker answer than it looks — it proves no *assertion* broke, not that nothing changed. Measure it directly: dump `computeDomainData(fixtureProjectPath(), FIXTURE_CONFIG, () => {})` as JSON via a scratchpad `tsx` script, then `git checkout <base> -- src/ test/ package.json package-lock.json && npm ci` to restore the pre-bump tree, dump again, `diff`, and restore. Do **not** reach for the CLI here: `FIXTURE_CONFIG` is held in memory precisely so the fixture stays byte-identical to canonical, so a CLI run would need a `domain-config.json` written into the fixture — mutating the thing being measured. This is how the c3source 2.0.0 section-narrowing was shown to be output-neutral in issue #48.

**When bumping `@genvidtech/mcp-utils`, audit `src/mcp/server.ts` for hand-rolled equivalents of its exported helpers** — the annotation constants, `mcpContent`, `paginatedContent`, and `withMcpErrors` all sat hand-rolled until the 0.4.0 bump adopted them (some had been available since 0.3.0). **The 0.7.0 floor is load-bearing for `OptimisticWatcher` + `ObservedState` (issue #68/#70, [ADR 0026](docs/decisions/0026-fs-watch-platform-confound-and-upstream-routing.md)), and that audit is what produced them.** `setupWatcher` had never been audited against `OptimisticWatcher`, which turned out to be its upstream equivalent — and the audit found the upstream one carried the *same* `txId` double-bump, because `ExpectedChanges.consume` is single-shot while Windows delivers two `fs.watch` events per write. So the fix went upstream first (`GenvidTechnologies/mcp-utils#12`) and shipped as 0.7.0's Layer 3, a content-fingerprint ledger with no timing term; this repo then adopted the whole watcher, which also retired the provably-dead `suppressWatcherDepth`. **It did *not* close the leaked `FSWatcher` handle (#70), despite `stop()` being the reason adoption looked like it would** — `shutdown()` calls `stop()`, but is wired only to `SIGINT`/`SIGTERM`, and a client disconnecting by closing stdin raises neither; the handle is `unref`'d in the watcher factory instead. **Two things that read as settled and are not:** `expected: ExpectedChanges` is a *required* option, so adoption does **not** retire that import; and `suppress()` is async-only, so `writeDomainConfig` stays synchronous by calling `expect()` instead — Layer 2 exists precisely for events arriving after the suppress window closes. Verify a release's actual API against the packed types (`npm pack @genvidtech/mcp-utils@<version>` → `package/dist/*.d.ts`), not just the release notes — **and read the packed `.js` when the question is about runtime *behaviour* rather than shape** (which argument a parameter applies to, what a default actually does, whether a guard is inherited). A `.d.ts` cannot express those, and issue #33 nearly shipped a worse-than-default mechanism on a `.d.ts`-only reading.

**When bumping `@genvidtech/c3source`, check whether new exports supersede local C3-parsing logic** — c3source owns the Construct 3 platform facts, so its releases tend to ship primitives that retire hand-rolled equivalents here. `extractFunctions`/`extractIncludes` (1.1.0) retired the local `src/domain/extraction.ts` walk in 0.2.0; `validateForEditor` (1.4.0) was adopted as `editorValidation.ts`; and 1.4.0's event-var-reference primitives (`getEventVarReferenceName`/`EVENTVAR_REFERENCE_ACES`, plus `visitEvents`/`hasConditions`/`hasActions`) were adopted in issue #14 — `computeDomainData` uses them to derive the second coupling source (`referencesFrom`/`referencedBy`); and `openProject`/`C3Project` (its section-dir coverage completed in 1.6.0/1.7.0) was adopted in issue #19 — `computeDomainData`/`validateEditorStrictness` use it for file discovery (ADR 0008); and 1.8.0's `collectAddonAttribution`/`getUsedAddons` were adopted in issue #25 as the project-wide `addon-inventory` diagnostic (ADR 0009); issue #26 then adopted the per-file `attributeObjectType`/`attributeFamily` counterparts as a per-domain addon-attribution diagnostic atop a new `objectTypeDirs`/`familyDirs` classification dimension (ADR 0010); and 1.8.0's `extractExpressionReferences` was adopted in issue #28 as the third cross-domain coupling source (`expressionRefsFrom`/`expressionRefsBy`, ADR 0011); and 1.9.0's caller-controlled `descend` parameter on `find_all_files_path`, with `isEditorLocalPath`/`C3_TS_DEFS_FOLDER`, was adopted in issue #33 to retire the last two hand-rolled `readdirSync` walks in `domainAnalysis.ts` (ADR 0013) — **but `descend` was then un-adopted in issue #47/#46/#51 (ADR 0017), which deleted its only call site. Do not cite `descend` when auditing why the floor is load-bearing: it no longer rests solely on `C3_TS_DEFS_FOLDER` (still consumed by `isReportableScriptDir`) — the 2.0.0 bump (issue #48, ADR 0021) added `isGeneratedScriptOutput` and the upstream-sourced `SCRIPT_SOURCE_EXTENSIONS` as further load-bearing reasons, described below. The floor is not ceremonial — but its justification moved, and that is exactly the kind of fact that reads as droppable to someone who only greps for the old reason.** Issue #52 (ADR 0020) continued the pattern: `find_all_files_path` itself lost its last call site too, retired in favor of the local `collectSectionFiles` seam — cite neither it nor `descend` when auditing the floor. As with mcp-utils, treat the release notes as a hypothesis and verify the actual surface against the packed `.d.ts` — **the issue's own example code is a hypothesis too**: #33's proposed predicate was wrong, because `find_all_files_path`'s `predicate` gates *files* by bare basename while `descend` gates *directories*, and neither inherits the other's editor-local filtering (the packed `.js`, not the prose, is what settled it) — **and `isEditorLocalPath` itself takes a bare *segment*, not a path**: hand it a multi-segment path and only the `.uistate.json` suffix test can fire, since `uistate`/`ts-defs` match as whole directory names and `tsconfig.json` matches exactly, so every other exclusion silently under-matches. A caller testing a *path* must walk its segments — `listInertOverrides` does, and that argument contract is where issue #36's `ts-defs/` trap lives (ADR 0018) — **and confirm the integration site the issue assumes actually exists** (issue #12 framed `validateForEditor` as a guard "before write-out," but this tool never writes C3 sheets, so it became a read-side diagnostic instead). **`SCRIPT_SOURCE_EXTENSIONS`'s retire-trigger fired and has been acted on.** `src/domain/classification.ts` (the `.ts`/`.js` script-source list, issue #39 / ADR 0016) used to be marked temporarily local, because 1.9.0 exported no script-extension constant (`findAllScripts` hardcoded `.ts` and excluded `.d.ts`). `GenvidTechnologies/c3source#73` requested it and closed merged on 2026-08-10, settling the `.js`/`.ts` disambiguation as a C3 platform fact rather than consumer policy (C3's own folder-project reconcile path implements exactly that rule); c3source 2.0.0 then shipped both the constant and its companion predicate `isGeneratedScriptOutput`, and issue #48 (ADR 0021) adopted both — `classification.ts` now re-exports `SCRIPT_SOURCE_EXTENSIONS` instead of defining it, and the local `isCompiledSibling` predicate it used to also define is **retired**, replaced at its two call sites by upstream's `isGeneratedScriptOutput`. `isScriptSourceName` (the admission predicate) stays local and is **deliberately not** replaced by upstream's same-named function: upstream's excludes `.d.ts`, where this tool must admit it to keep ADR 0013's `ts-defs/` exemption indexable — pinned by a cross-library test in `test/domain/scriptSurfaces.test.ts`. **A second, separate upstream question: `GenvidTechnologies/c3source#76`** asked whether the four section collectors' extension policies were intentionally inconsistent (`findAllEventSheets`/`findAllFamilies` filtered to `.json`; `findAllLayouts`/`findAllObjectTypes` didn't — measured, ADR 0017). c3source 2.0.0 answered it by unifying all four finders to filter `.json` upstream, via the AUDITED `isSectionItemName`/`C3_SECTION_ITEM_EXTENSION`. **The local section-extension constant and predicate's own retire-trigger has since fired too, and issue #60 (ADR 0022) acted on it.** ADR 0020 had been misread here as holding the `.json` list as this repo's own policy — that framing was a `CLAUDE.md` gloss, never ADR 0020's own text, which adopted `.json` as "c3source's own documented convention, not inventing a new one." With upstream's predicate agreeing with the retired local one on every basename measured, the re-examination concluded in retirement — but **note the route, because it is the part that generalizes**: `#73` was a *deletion trigger* that fired on its own, while `#76` was only a *prompt*, and it took issue #60 examining the question to reach the same destination. Same outcome, different mechanism; do not collapse the two when the next upstream question closes. See the Classification section below for what did and didn't transfer, and `docs/decisions/0022-section-extension-provenance.md` for the full accounting.

## TypeScript / module setup

- Pure ESM (`"type": "module"`), `NodeNext` resolution, Node >= 22. Relative imports **must** use `.js` extensions even though sources are `.ts`.
- **Reading the package's own files at runtime:** `process.cwd()` is the *target* Construct 3 project, **not** this package — `cli.ts` derives the source root from `--project-dir`/cwd via `resolveProjectRoot` and `server.ts` defaults `PROJECT_ROOT = process.cwd()`, for exactly that reason. To read a file shipped *with* `c3-domain-manager` itself (e.g. `package.json` for the CLI `--version`), resolve it relative to the compiled module via `path.dirname(fileURLToPath(import.meta.url))`, **never** `cwd`. The compiled entry is `dist/cli.js`, so the package root is one level up (`../package.json`). Yargs' own version auto-detection does *not* find it — wire `.version()` explicitly (this was the `--version: "unknown"` bug, issue #3).
- The package entry points (`main`/`types`/`exports`) point at the compiled `dist/*.js`/`*.d.ts` directly. Development never imports the package by its own name (tests use relative `.js` paths), so there's no dev/publish entry-point swap — `dist/` is built by `prepack` (and the CI gate) before anything consumes those paths. `publishConfig` holds only `{ "access": "public" }`.
- **Publish pitfall:** keep `main`/`types`/`exports` at the **top level** pointing at `./dist/...`; do **not** move them into `publishConfig`. npm 11.x no longer applies `publishConfig` field overrides for entry points — it would ship the top-level values and warn "Unknown publishConfig config", so a package that hides its `dist/` paths inside `publishConfig` publishes source-pointing entry points that are unresolvable under `NodeNext` (this class of bug broke `@genvid/c3source@0.3.0`, fixed in 0.3.1). Verify against the packed manifest (`npm pack`), not the dry-run notice alone.
- Two tsconfigs: `tsconfig.json` (composite, `src/` only, emits `dist/`) drives the build; `tsconfig.test.json` (`noEmit`, includes `test/`) drives `typecheck`.

## Architecture

The analysis core lives in `src/domain/` and is pure and I/O-light. The CLI (`src/cli.ts`) and the MCP server (`src/mcp/server.ts`) are thin adapters over it. Code shared *between* those two adapters lives in `src/adapters/` (e.g. `locations.ts` — the `resolveLocations` seam that resolves the config path, extracted-output dir, and ephemeral-temp behaviour from CLI flags / `startServer` options); it is deliberately **not** re-exported from the public API. `src/index.ts` is the public library API (re-exports everything in `src/domain/` only) — so **a new `src/domain/` module must add its own `export * from "./domain/<name>.js";` line here**; it's easy to forget when creating a module (code review caught `coupling.ts` missing it in issue #30).

**Computation vs I/O split** — the key pattern in `domainGenerator.ts`:
- `computeDomainData(rootDir, config, log)` is the pure heart: walks the project, classifies files, parses event sheets, and resolves cross-domain dependencies, returning `{ domains: DomainData[], unclassified: string[] }` with no writes.
- `generateDomainIndex(...)` wraps it for I/O: it is **async** and takes `(rootDir, outDir, configDir, configFileName, log)`. It loads the config via the async throwing `loadConfig(configDir, configFileName)` (a thin wrapper over mcp-utils' `loadProjectConfig` that validates against `DomainConfigSchema` and throws a `loadProjectConfig(...)`-prefixed `Error` on failure, keeping MCP types out of the pure core), calls `computeDomainData`, then wipes and rewrites `extracted/domain-index/` (a master `index.md` plus one page per domain). The MCP server bypasses this wrapper and calls `loadProjectConfig` directly so its tool handlers can return the structured `CallToolResult` error verbatim. The config path is split into `configDir`/`configFileName` by `resolveLocations` so an absolute, outside-root `--config` still resolves (`path.join(configDir, configFileName) === configPath`).

**Classification** (`classification.ts`, `classifyFile`) decides which domain a file belongs to:
1. Exact-path `overrides` win first.
2. Otherwise the file's path (after stripping its file-type root `eventSheets/`|`layouts/`|`scripts/`) is matched against each domain's `*Dirs` arrays, **longest matching prefix wins**.
3. Both `domains` and `sharedSubdomains` participate in matching.
Files matching nothing become `unclassified`. `classifyFile` tolerates **one trailing slash** on its path argument, so a `findScriptEntries` directory entry (`scripts/other/`) classifies directly and the same string works as an `overrides` key (ADR 0017). `classification.ts` also exports the authored-script predicates (`SCRIPT_SOURCE_EXTENSIONS` / `isScriptSourceName`) that both script-enumerating surfaces use to admit `.ts`/`.js`; the other four sections share one enumeration, `collectSectionFiles`. Since c3source 2.0.0 (issue #48, ADR 0021), `SCRIPT_SOURCE_EXTENSIONS` is **re-exported from c3source** rather than defined locally, and compiled-sibling suppression is upstream's `isGeneratedScriptOutput`, imported directly at the two walk sites (`findScriptEntries`, the `listUncategorized` script walk) in place of the retired local `isCompiledSibling`. `isScriptSourceName` stays local **by deliberate choice, not by gap**: c3source exports a same-named function since 2.0.0, but it excludes `.d.ts`, where this tool's version must admit it to keep ADR 0013's `ts-defs/` exemption indexable — the divergence is pinned by a cross-library test in `test/domain/scriptSurfaces.test.ts`. The local section-extension constant and predicate are **removed**, not merely unreachable (issue #60, ADR 0022): the parse-boundary policy ADR 0020 adopted was always upstream's convention, not this repo's own, and the retired local predicate agreed with upstream's `isSectionItemName` on every basename measured, so nothing was gained by keeping a local duplicate. `collectSectionFiles` is now a pure relativize-and-map with no admission rule of its own — every `C3Project.findAll*` collector it wraps already admits only `.json` name-section items via upstream's AUDITED `isSectionItemName`/`C3_SECTION_ITEM_EXTENSION` before `collectSectionFiles` ever sees the result. `domainAnalysis.ts`'s `listInertOverrides` imports `isSectionItemName` directly at its one class-3 call site; unlike `isScriptSourceName`, no local wrapper survives, because there is no divergence to protect (contrast the `.d.ts` divergence just above). The ordering hazard — `Main.uistate.json` ends in `.json`, so `isSectionItemName` alone would re-admit it — is now a property of upstream's predicate contract (composed into `find_all_section_items_path` ahead of any call site here), not of a local symbol's docstring; `listInertOverrides`' class-3 comment records it at the one place it is actually load-bearing. It also exports `isReportableScriptDir(name)`, the `scripts/` directory-descent rule that deliberately exempts `ts-defs/` from c3source's editor-local list (moved here from `domainGenerator.ts` in issue #36 once it had two readers, `findScriptEntries` and `listInertOverrides`; ADR 0018) — and `hasClaimBelow(innerPath, fileType, config)`, which reports whether any `*Dirs` entry or `overrides` key claims a path *strictly below* a directory. Its prefix test is anchored on `innerPath + "/"`; unanchored, `scriptDirs: ["common2/x"]` would match `common` (ADR 0017). **`FILE_TYPES` carries a third per-section field beyond `root`/`dirKey`: `emitsDirectories`** — can this section's walk ever produce a *directory* entry? Only `scripts/` can; the other four go through `collectSectionFiles`, whose `C3Project.findAll*` collectors yield files only. **That reason changed in issue #52 while its conclusion did not** — before ADR 0020 the four walked `find_all_files_path` directly, and this sentence still said so afterwards. Nothing failed: the field's *value* stayed right, so no test, type-check or reviewer had anything to catch. Exactly the decay ADR 0020 itself is about, one level up. Its `satisfies` constraint forces a new section to **supply** the field, but cannot force the **right value** — that is answerable only by reading that section's walk, so the type error is a prompt, not a guarantee. `listInertOverrides` uses it to decide whether a directory-shaped override key is even *askable*, and then consults `findScriptEntries` itself for the answer: under `scripts/` liveness depends on the walk's descent decisions (`isReportableScriptDir`'s `ts-defs/` exemption, `LAYER_DIRS` recursion, `hasClaimBelow`-forced descent), not on the section, so **the table gates the question and the walk answers it**. A static table alone gets it wrong three distinct ways — measured in issue #54, recorded in ADR 0019.

**Cross-domain dependencies** are derived from three sources in `computeDomainData`. First, `include` events: `extractIncludes` (from `@genvidtech/c3source`) walks the event tree and `domainGenerator` maps each included sheet back to its owning domain to build the `includesFrom` / `includedBy` graphs. (Before 0.2.0 this walk was hand-rolled in a local `src/domain/extraction.ts`, since retired.) Second, event-variable references (issue #14): `extractEventVarDecls` indexes top-level variable declarations per domain, and `extractEventVarRefs` collects System-ACE references via `getEventVarReferenceName` + `visitEvents`/`hasConditions`/`hasActions`; `computeDomainData` then resolves references to declaring domains and builds the sibling `referencesFrom` / `referencedBy` graphs. Resolution policy: global-scope approximation (root-level decls only), attribute-to-all on name collision, unresolved and same-domain references produce no edge. Third, expression (member) references (issue #28 / ADR 0011): `extractExpressionRefs` walks raw ACE parameter strings and `computeDomainData` resolves object/family member references (via an `objectNameIndex` built from the `objectTypeDirs`/`familyDirs` classification) into the sibling `expressionRefsFrom` / `expressionRefsBy` graphs, under the same union semantics. On top of all three, an opt-in `coupling` config block (`discountSharedKernel`/`hubDomains`) applies a **consumption-time** shared-kernel hub discount — an edge to a hub domain is discounted uniformly across every consumer at read time, while the raw graph in `DomainData` stays fully built (issue #30 / ADR 0012; the pure predicate lives in `src/domain/coupling.ts`). See `docs/domain-architecture.md` for the full policy and how all three edge kinds (and the discount) are aggregated in health, boundary validation, context map, and domain pages. `extractFunctionDefs(sheet, sheetName)` remains the seam for mapping `extractFunctions` results onto our local `FunctionDef` (param-string formatting + `sourceSheet`/custom-ACE fields).

**Every section has exactly one enumeration** (`scripts/`: issue #47/#46/#51, ADR 0017, a third reader arrived in #54 / ADR 0019; the other four: issue #52, ADR 0020). `findScriptEntries` (`domainGenerator.ts`) is `scripts/`'s; `collectSectionFiles` (`classification.ts`) is the shared one for `eventSheets/`, `layouts/`, `objectTypes/` and `families/`. `computeDomainData` and `listUncategorized` consume both; `validateEditorStrictness` (`editorValidation.ts`) also consumes `collectSectionFiles` — for `eventSheets/` only, never `findScriptEntries`, since it validates event sheets rather than scripts; `listInertOverrides` additionally consults `findScriptEntries` directly, because only `scripts/` can ever produce a directory-shaped override key (`FILE_TYPES.emitsDirectories`) that needs checking against the actual walk — the other four sections never emit directories, so `listInertOverrides` rules out a directory-shaped key for them without walking at all. `domainAnalysis.ts` imports `findScriptEntries` from `domainGenerator.ts` — the one edge between those two modules, and it must stay pointing that way; `collectSectionFiles` deliberately lives in `classification.ts` instead, keeping that edge single-purpose. **The invariant is the number of enumerations, not the number of readers** — this sentence said "two readers" until #54 added a third, which is exactly the kind of count that decays every time a consumer is added. Adding a reader is fine and expected; adding a second *walk* for a section is what re-opens that section's divergences below. What a second walk actually forbids is a *contradicting* second view of one section's set — two walks that can disagree because one applies a suppression rule the other doesn't. A read-side traversal with no suppression rule to contradict is acceptable precedent (ADR 0021, restated in ADR 0022, and relied on by ADR 0023's revival guidance): `editorValidation.ts` was that precedent's exemplar in `src/` until issue #37 routed it through `collectSectionFiles` anyway, for idiom locality rather than because the second walk was unsafe (ADR 0024) — the precedent survives, it just no longer has a live exemplar in `src/`. The decision behind it is the definition of the command: **`list-uncategorized` is the worklist for the domain index** — a path is reportable exactly when assigning it to a domain would change what the index contains. That is derivative, not independent, and it is what stops each section's surfaces drifting apart again; for `scripts/`, three separate divergences (a granularity mismatch, an allowlist, an extension filter) all came from having two walks. `findScriptEntries` remains a hand-rolled `readdirSync` walk **by design** — it must emit *directory* entries, which `collectSectionFiles`'s `C3Project.findAll*` collectors cannot — so `scripts/` keeps a *different* admission rule (`isScriptSourceName`, `.ts`/`.js`, local by a deliberate `.d.ts` divergence from upstream, ADR 0016/0021) from the other four, which as of issue #60 (ADR 0022) have **no** local admission rule at all — `.json` is admitted entirely inside c3source's own `C3Project.findAll*` collectors, via the AUDITED `isSectionItemName`, before `collectSectionFiles` ever runs: one enumeration per section is the shared property, a shared extension rule is not. `findScriptEntries` also takes an optional `config` so it can descend into a directory the config claims *below* — without it, a `scriptDirs` entry naming a nested subtree silently lost that subtree from the index. Anything that re-adds a second walk for any section re-opens its divergences. The `scripts/` invariant is pinned by a full-tree agreement test in `test/domain/scriptSurfaces.test.ts`; the other four are pinned by `test/domain/sectionSurfaces.test.ts`.

Downstream analysis modules all consume `DomainData[]`: `health.ts` (Ca/Ce/instability), `relationships.ts` (`validateBoundaries` — declared vs. observed deps), `glossary.ts` (cross-domain term collisions), `contextMap.ts` (text/Mermaid), `domainAnalysis.ts` (`listUncategorized`, `listStaleOverrides`, `listInertOverrides`, override validation). `formatting.ts` renders everything to markdown/text. `editorValidation.ts` (`validateEditorStrictness`, `formatEditorStrictnessReport`) is a read-side diagnostic that enumerates `eventSheets/` through `collectSectionFiles` — the same seam the domain index uses — and does not consume `DomainData[]`, attributes each sheet to a domain via `classifyFile`, calls `validateForEditor` per sheet, and returns issues grouped by sheet; unclassified sheets are still validated and reported under `"(unclassified)"`.

All domain types are defined in `src/domain/types.ts` (`DomainConfig`, `DomainDefinition`, `DomainData`, `Relationship`, `FunctionDef`). The config types (`DomainConfig`/`DomainDefinition`/`SharedSubdomainDefinition`/`Relationship`) are **schema-first**: `DomainConfigSchema` is the source of truth and the types are `z.infer` of it. The schemas are lenient — `.passthrough()` so unknown keys survive the load→mutate→write round-trip, with non-essential fields optional and `description` required.

### MCP server specifics (`src/mcp/server.ts`)

- Auto-generates the domain index on startup if `extracted/domain-index/` is absent.
- Holds mutable state behind a `ReadWriteLock`: a `txId` (monotonic) and a `domainDirty` flag. Mutate tools (`set-overrides`, `remove-overrides`) edit the target's `domain-config.json` and set `domainDirty`; their handlers are wrapped in `withMcpErrors` so any thrown error (e.g. a failed `fs.writeFileSync`) is returned as a `CallToolResult` error rather than crashing the server. An `onError` hook (`onWriteError`) bumps `txId` on write failure so the client knows to reconcile after a possibly-partial write. Successful mutate responses are built with `mcpContent(body, footer)` which appends the current `txId` as a trailing footer line. Read tools that depend on the index append a stale warning until `regenerate` clears it.
- Tools accept an optional `txId` for optimistic concurrency — a write is rejected if it doesn't match the server's current `txId` (read it via `get-state`).
- Tool annotations classify each tool as `READ_ONLY`, `REGENERATE`, or `MUTATE`.
- The `validate-editor` tool (`READ_ONLY`) intentionally does **not** append the stale-index warning: it re-walks event sheets fresh from disk and never reads the cached domain index, so index staleness is irrelevant to its output.

## Documentation conventions

Docs under `docs/` (especially ADRs in `docs/decisions/`) are committed and read by people who do not share this machine. Several rules follow:

- **There is a third documentation tier beyond this file and `docs/`: the wiki at `wiki/`, whose defining property is that every claim states where it came from.** An ADR is scoped to one decision at one moment, so knowledge spanning several records — what `fs.watch` does per platform, when to route a fix upstream — used to have nowhere to live but *this file*, where it drifts. A wiki page is a summary that carries per-claim footnotes resolving through frontmatter `sources[]` to a fixed artifact, which is exactly what the drift instances below lacked. `docs/wiki-schema.md` is the maintenance contract; `/gvt-dev:maintain-wiki` is the interface (`ingest` / `query` / `lint`). Two rules are load-bearing and easy to violate without seeing them: **in-repo records are cited directly, never snapshotted into `raw/`** (git already provides that immutability, and a snapshot is a second copy that drifts from the record it copies), and **`CLAUDE.md` is not citable as a source** — it is rewritten continuously, so a page citing it cannot be re-verified against a fixed text, which is the one property `sources[]` exists to guarantee. A claim worth a wiki page and found only here needs an ADR or an issue behind it first. Note also that **nothing automatic checks wiki link health or staleness**: `lint` is on-demand and is deliberately never wired into `audit-conventions`, so that wiki content can never move a contract audit's exit code (issue #72).

- **A sentence in *this* file that characterizes an ADR's *framing* is a second copy of that ADR, and it drifts.** Citing a record by number is safe; paraphrasing what it *decided* is not — the paraphrase reads with the record's authority while carrying none of its text, and nothing compares the two. So quote the record, or `grep` the paraphrase against it before relying on it. This is not hypothetical and the cost is not small: **`SECTION_SOURCE_EXTENSIONS` was described here for months as "product policy, local by decision — derived from what `computeDomainData` parses, not from what C3 permits on disk," a phrase that appears nowhere in ADR 0020.** ADR 0020 decided the opposite — it adopted `.json` as *"c3source's own documented convention, not inventing a new one."* The gloss survived long enough to shape issue #60's problem statement, a requirements analysis, and a design before one `grep` settled it (ADR 0022). Note which way the error ran: the *record* was right and the *summary* was wrong, so a reader trusting this file over `docs/decisions/` got it backwards — the reverse of the staleness this file usually warns about.

- **The same rule holds *between* records, which is the larger surface — an ADR paraphrasing a sibling's reasoning is a second copy too.** The bullet above is written about *this* file, and that scoping reads as the whole rule; it is not. Sibling citation is near-universal (22 of 23 records carry a `[[slug]]`), so record-to-record paraphrase happens far more often than `CLAUDE.md`-to-record paraphrase does. Citing a sibling's *conclusion* is safe. Restating the *route it took* is not — and **two records reaching the same answer by different arguments is the common case, not the exception**, so the paraphrase that feels safest (the conclusions match, after all) is exactly the one that silently swaps mechanisms. ADR 0023 credited ADR 0020 (`docs/decisions/0020-section-source-extension-filter.md`) with a manifest-position argument — a name section keys its items on `<name>.json`, so a stray has no position to acquire — that appears nowhere in it; `grep` finds no keying reasoning in ADR 0020 at all. Its actual route was that nothing downstream can represent the file, so no `overrides` entry could usefully change anything. The keying argument is *upstream's*, and the two are not interchangeable: one is about C3 manifest position, the other about this tool's index representation. Caught in review before merge (issue #62). So: `grep` the sibling before attributing a mechanism to it, and where two records agree by different routes, **say that** rather than collapsing one into the other. Note this bullet and the one above are the same failure at two altitudes — the fix for both is that a citation carries authority the citing text has not earned until someone compares them, and nothing does that automatically.

- **A third shape needs no second artifact at all — a bolded headline that overreaches the paragraph it introduces.** The two bullets above each compare a summary against a *separate* record, which at least tells you what to `grep`. This one is self-contained, and so has no natural prompt to check it: the section-enumeration paragraph's headline used to assert not just that each section has one enumeration but that *every reader goes through it* — while the same paragraph stated, eight sentences later, **"The invariant is the number of enumerations, not the number of readers"**, and that adding a reader is fine and expected. (The retired clause is quoted verbatim in `b64ef18`; it is deliberately not reproduced here, because a criterion pinned to its absence is what proves it gone.) The headline clause had zero support in `docs/decisions/`, and the qualifier contradicting it was *already present* and still did not prevent the misframing — because a headline is what a reader orients on and the body is what they skim. It sent issue #37 into a requirements analysis and a design resting on a premise three accepted records deny, unwound only by reading those records directly ([ADR 0024](docs/decisions/0024-editor-validation-single-enumeration.md)). So: a bolded claim in this file is load-bearing in a way the sentences beneath it are not, and when a paragraph qualifies its own headline, the headline is the thing to fix — not the qualifier to add.

- **A fourth shape: a dispatch brief is a paraphrase too, and it is the one the reader cannot check.** The three above all end up in a committed file, where a later reader can at least `grep` them. A brief handed to a subagent never lands anywhere — it is consumed once, by a context that has no independent access to what it summarizes and every reason to treat it as authoritative. Measured in issue #72: a brief dispatching `tech-writer` to author `wiki/documentation-drift-modes.md` supplied three worked examples drawn from *this file*; on reading the records, **two of the three did not exist in the ADRs the brief attributed them to** — one described an error caught in review before merge, so the merged record is clean, and one traced to a `CLAUDE.md` sentence with no ADR behind it at all. Both were replaced with ADR-traceable equivalents. What caught it was a single instruction in the brief telling the agent to read the ADRs and write from them rather than from the brief's summary; without that line the fabricated attributions would have shipped *inside the page about fabricated attributions*. So: name the primary sources in a brief and require the agent to read them — never let a summary in the brief stand in for the record, and treat a brief that says "the ADR decided X" as owing the same `grep` as a sentence in this file would.

- **Never cite a machine-local path.** Design work here is often validated against real Construct 3 projects checked out locally. Those measurements are valuable and belong in an ADR — but cite the *measurement and the project's characteristics* ("a large domain-foldered project, C3 r47604, 245 `.uistate.json` files"), never the path (`C:\repos\<name>`). A reader cannot follow the path, and the checkout may not survive.
- **Verify every cross-reference before writing it.** A link or section name that does not exist is worse than no citation — it sends the next reader hunting. This bit issue #33: a drafted ADR cited a `CLAUDE.md` section named "Real C3 project corpus" that has never existed in this file. Auto-memory and `<system-reminder>` content sit in the same context window as repo content but are **not** part of the repo; treat them as input you may act on, never as something you may cite. `grep` the target file before asserting a section exists.

- **ADR cross-references use `[[<adr-slug>]]`, not markdown links.** A sibling record is cited as `[[0011-expression-reference-coupling]]` — bare filename stem, double brackets, no path, no `.md`. Prose references by number (`ADR 0013`) coexist and are equally fine. **Do not "normalize" the bracket form away:** it is the house style in every record but one (`0008-adopt-openproject-option-a`, currently 22 of 23), not a stray. This is easy to get backwards, because auto-memory files use the same `[[name]]` syntax for *their* links — so the form reads like a leak from outside the repo, the mirror image of the trap in the bullet above. Check `docs/decisions/` before concluding a convention is foreign; a two-file sample is not the corpus. **The form stops at that directory, though — it is how a *record cites a record*, not a repo-wide link style.** Prose docs cite ADRs by path: `docs/domain-architecture.md` does so at all six of its citation sites, and `README.md` carries none. So a `[[slug]]` reaching a non-ADR doc is over-application, not adoption — the failure mode is the mirror of the one this bullet already warns about, and it happened in issue #39 (caught in review, one line).

- **In a code comment, cite the *symbol*, not a line range.** The bullets above are about prose drifting from a record; this one is about a citation drifting from *code*, which decays far faster and is invisible to every gate here — lint, typecheck and the full suite stay green because nothing reads comment prose. Measured: `test/mcp/writeFailure.test.ts`'s citation of the config-path watch handler went stale **twice in two days** — corrected `server.ts:598-606` → `602-610` in issue #68's first branch commit, then invalidated again one commit later by the `OptimisticWatcher` adoption, which moved the handler again. Re-numbering only resets the clock; a symbol name (`onExternalChange`) survives every edit that does not rename it, and a rename is exactly when the next reader should be looking anyway. **Two carve-outs.** ADRs are exempt — a record documents state at decision time, so "correcting" its line numbers falsifies it rather than maintaining it (`docs/decisions/0025-*.md` cites `server.ts:34-40`, now stale, and is deliberately left alone). And `file:line` in *this* file, in an issue body, or in a dispatch brief is fine: those are working references read once, not committed alongside the code they point at.

- **A `grep` miss is not evidence of absence — check the pattern before concluding the doc is silent.** This file is dense with `**bold**`, backticks and em-dashes, so a plain-looking phrase often carries markup mid-token. A retro this file prompted nearly proposed re-adding the "a dependency major can land **mid-task**" rule as a gap, because the grep for it spanned the `**` and returned nothing — the rule was already here, three lines from where the addition would have gone. Anchor on a distinctive unbroken substring, or `grep -c` a couple of variants, before writing "not documented".

- **Six optional `audit-conventions` doc expectations are unmet by decision, not by neglect** — `docs/architecture.md`, `docs/design-patterns.md`, `docs/coding-conventions.md` (declared by `ts-implementer`) and `docs/code-review-{context,patterns,docs}.md` (declared by `code-reviewer`). Every audit run lists all six under `### Info (optional)`, which reads as a backlog. It is not one: that content lives in this file and in `docs/domain-architecture.md`, and splitting it out would create exactly the second-copy-that-drifts problem the bullets above are about. All six are declared `required: false` precisely so a repo that keeps the content elsewhere still passes. Leave them absent unless the content genuinely diverges from what this file carries.

ADRs are numbered chronologically and **self-indexed** in `docs/TOC.md` under `## Decision Records` — one line ending with the issue number in parens. An ADR that is not indexed is invisible to the planning skills.

## Testing conventions

Tests use mocha + chai (`assert`) and run through `tsx` (no build needed). `test/setup.ts` is a mocha root-hook plugin that silences `console.log`/`console.debug` during each test (leaving `warn`/`error`) — diagnostic logging in the core is passed in as a `log`/`Logger` callback, so prefer that over global console output. Tests live under `test/domain/` mirroring `src/domain/` — **with exceptions**: there is no `classification.test.ts`; `classifyFile` (from `src/domain/classification.ts`) is tested in `test/domain/domainFormatter.test.ts`. When touching a module, grep for its symbols across `test/domain/` rather than assuming a same-named test file.

**Note `test/setup.ts` root hooks must be named `beforeAll`/`beforeEach`/`afterAll`/`afterEach`.** Mocha's root-hook plugin API recognises only those four; a `before` or `after` key is **silently ignored** — the hook never runs and nothing reports it. This is how the fixture guard below first shipped broken.

### The canonical fixture

Two kinds of test coexist in the same files. **Synthetic** tests build a C3 project in a per-test `fs.mkdtempSync` dir; **fixture-backed** tests (`describe("… — canonical fixture")`) run against the real `construct3-sample` project. Both are needed, and which to reach for is not a style preference:

- **Fixture-backed** for "does this hold against a real C3 export" — the manifest, real event sheets, all three cross-domain coupling edges, the folder shapes.
- **Synthetic** for anything requiring a **negative** case the fixture does not contain. The fixture tracks no `*.uistate.json` (upstream gitignores it — the editor rewrites it on every open, so its content is churn, not signal), so a fixture-backed "no uistate in the output" assertion would pass without exercising the exclusion, and would keep passing if the exclusion were deleted. **Never assert the absence of something the fixture never had.** See ADR 0014.

`test/fixtures/construct3-sample` is a submodule pinned to a **tag** (currently `v1.0.0`); `scripts/prep-fixture.mjs` materializes it into the gitignored `test/fixtures/canonical/` via `git archive HEAD` + `fflate` (a **declared devDependency** — it also arrives transitively through `@genvidtech/c3source`, but relying on that would be a phantom dependency a future c3source change could remove silently), deleting and rebuilding each run, so the fixture is a pure function of the pinned commit and cannot pick up untracked or locally-modified bytes. CI checks the submodule out through the shared gate's `submodules: recursive` input — the prep script does **not** self-init.

All fixture access goes through `test/fixtureHelpers.ts`: `fixtureProjectPath()`, `PROJECT_FIXTURE` (the single swap point — no test builds a fixture path itself), `FIXTURE_CONFIG` (the domain config, held in memory so the fixture stays byte-identical to canonical), and `assertFixtureMaterialized()`, which **throws** from a root `beforeAll` rather than letting tests skip. Per-test `if (!exists) this.skip()` guards are banned: a skip turns a missing fixture into a passing suite, and mocha renders a permanently-skipped test identically to an intentionally pending one.

Shared test helpers live in flat, concern-named modules directly under `test/`, siblings to `setup.ts`, with no `.test.` infix so the mocha glob doesn't pick them up: `fixtureHelpers.ts` (the canonical fixture — `PROJECT_FIXTURE`, `fixtureProjectPath`, `FIXTURE_CONFIG`, `assertFixtureMaterialized`), `syntheticProject.ts` (throwaway C3 projects — `createFile`, `makeTempDir`, `removeTempDir`, `makeObjectType`, `makeFamily`), `domainModel.ts` (in-memory literals — `makeConfig`, `makeDomain`), and `mcpHarness.ts` (the subprocess MCP stdio harness — `startHarness`, `textOf`/`assertOk`/`assertToolError`/`txIdOf`, `SELF_WRITE_OBSERVED_TXID_BUMPS`; see ADR 0025). The naming encodes the synthetic/fixture split: `syntheticProject.ts` and `mcpHarness.ts` must never import `fixtureHelpers.js`.

**`test/fixtures/` is excluded from lint and typecheck** (`.eslintrc.cjs` `ignorePatterns`, `tsconfig.test.json` `exclude`) — the fixture ships 56 `ts-defs/*.d.ts` using `var`/`Function`, which the rules forbid at `--max-warnings 0`. CI runs lint and typecheck *before* test, so without these a clean first run passes and every cached run fails. Do not remove them.

**Changing the sample itself is a different job from bumping the pin.** `construct3-sample` is an upstream repo with its own contribution protocol: project JSON must come from a **Construct 3 editor round-trip**, not be hand-authored, because a real editor save completes half-authored data — and c3source's parser types fields the editor *requires* (`variable.comment`, `group.description`) as optional, so a green automated gate does not prove the project loads. Read that repo's `README.md` before editing it. Drafting the edit programmatically and *then* importing and re-saving in the editor satisfies the protocol; skipping the round-trip does not. Enrichment ends in a new tag, and the pin moves to it.

**Bumping the pin:** update the gitlink → `npm run fixture:prep` → **re-capture** every fixture-backed assertion by running the real functions. Those values were measured, not derived; adjusting them to make tests pass would defeat the point. No manual C3-editor checkpoint is needed here (that belongs to *producing* a `construct3-sample` release — this repo is read-only and inherits load validity from the tag).

**Extending `DomainData` costs one edit, in `test/domainModel.ts`.** That module's `makeDomain(name, opts?)` enumerates every `DomainData` field (no spread from a real `computeDomainData` call), so adding a **non-optional** field to `DomainData` (`src/domain/types.ts`) breaks `tsc` there until its literal is updated. Before issue #38 this helper was hand-rolled in seven copies across six test files, and the same one-line fix had to be applied to each — which bit the issue #26 addon-attribution work and again in issue #28.

**The MCP server (`src/mcp/server.ts`) has a subprocess-based stdio test harness** (`test/mcpHarness.ts`), driving the real server over its production CLI path with a real MCP `Client` — see `docs/decisions/0025-mcp-server-stdio-test-harness.md`. `test/mcp/tools.test.ts`, `test/mcp/mutation.test.ts`, and `test/mcp/writeFailure.test.ts` now cover tool-level `isMcpError`/`CallToolResult` propagation, `domainConfigCache` invalidation on both self-writes and watcher events, optimistic-concurrency `txId` rejection, the mutate-tool `withMcpErrors`/`onError` write-failure path, and the `mcpContent`/`paginatedContent` response shapes (single-block output, stale-warning footer) — the five behaviours this section used to name as untested. What the harness still does not cover: it is black-box over stdio, so module state (`txId` — now the watcher's, `domainDirty`, the two caches) is observable only through tool responses and logging notifications, never directly; an in-process harness driving the registered tool callbacks themselves (Route 2 in ADR 0025) remains unbuilt; and anything not reachable through one of the 14 registered tools is untested by construction. The `txId` double-bump (#68) and the leaked `FSWatcher` handle (#70) are **fixed**, by adopting mcp-utils 0.7.0's `OptimisticWatcher` — see [ADR 0026](docs/decisions/0026-fs-watch-platform-confound-and-upstream-routing.md). `SELF_WRITE_OBSERVED_TXID_BUMPS` is now `1` and K3 asserts unconditionally. **Note what fixed #70, because the obvious answer is wrong:** `shutdown()` does call `watcher.stop()`, but `shutdown()` is wired only to `SIGINT`/`SIGTERM`, and a client disconnecting by closing stdin raises neither — so `stop()` is never reached on that path. The handle is `unref`'d in the watcher factory instead; measured, the server was still alive 8s after stdin close both before *and* after adoption until that landed. There is also no async-rejection helper (`chai-as-promised` is not installed) — assert on rejected promises with `try/catch` + `assert.include(err.message, ...)`.

**Three shapes of the harness's own defaults that cost round-trips if guessed** (all reachable by reading `test/mcpHarness.ts`, but easier stated): `startHarness()` builds its project from `makeConfig({ Domain0: … })`, so the domain to classify into is **`Domain0`** — a `set-overrides` naming anything else comes back as a tool error, not a `txId`; `config.domains` is a **keyed object, not an array**, so an external-write probe assigns `cfg.domains.Name = {…}` rather than pushing; and `LogNote.data` is typed `unknown`, so a notification filter needs `String(n.data)` before any regex. **Also note what the harness structurally cannot see:** its `StdioClientTransport.close()` kills the child, so no suite test can observe whether the server would have exited on its own — that is why #70 needed a standalone probe that closes stdin and waits, and why a green suite said nothing about it either way.
